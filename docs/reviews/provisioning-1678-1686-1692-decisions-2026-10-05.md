## Findings made while building (all reproduced on temp trees)

- N1. `icacls /T /L` still reaches through a directory symlink (D7). A junction is not followed.
- N2. `icacls` cannot remove or add an entry for a deleted account (exit 1332): the orphan removal is done directly.
- N3. An elevated token renames and deletes a folder that carries an explicit Delete deny and a Delete-child deny; a de-elevated token cannot. Relevant to the swap defence only if a coder were elevated (it is not).
- N4. `acp_coder.build_env` (BlarAI repo, not touched here) hands the opencode child a fixed environment whitelist: the git environment set in the runner does not reach opencode's shell. Read-only `git status` still works; "dubious ownership" on operator-created worktrees needs the coder's own `.gitconfig` (plan step 4) or a `build_env` change. Needs its own ticket in the BlarAI repo.
- N6. `runas /trustlevel` (the first de-elevation route) starts the child in a NEW VISIBLE CONSOLE: that was the blank windows. Replaced (D13, D14). The first version of this suite also launched children with a plain `&` from a host that could have had a console; all now go through the hidden launcher.
- N5. The previous "targeted undo" listing was computed from the current ACL, so it was empty for any action already applied (D8).

## What is NOT verified

- Nothing ran against the real coder account, the real `C:\`, `B:\`, `C:\blarai-fleet`, `C:\Users\mrbla\projects` or the real scheduled task. Checks 5-14 of `verify-coder-containment.ps1` have never run against a real coder token; the temp-tree self-test uses the current user, de-elevated, as a stand-in (one token cannot be both operator and coder, so the operator steps run in a temporary "operator window" whose end state is asserted).
- The size and duration of the real tree walks (45 repos plus any `.venv`/`node_modules`): the dry run prints the object counts; the apply time is unmeasured.
- Whether the real `B:\models`, the production model folder and `C:\Users\mrbla\BlarAI` actually carry the writers/orphan the tickets describe: the plan reads them at run time; the dry run is where that is seen.
- That Windows propagates the changes to children that have inheritance enabled exactly as on the temp tree (it did there); repos with inheritance OFF are listed by the dry run and get no read entry (the coder cannot read them until granted by hand).
- The `-Credential` direct-spawn mode of `verify-coder-containment.ps1` with the new array arguments (the scheduled-task mode is the exercised path).
- Opencode's behaviour under a READ-only projects folder: a real watched fused dispatch is the test (plan step 7). Anything the coder tooling writes beside the source tree (caches, lock files) that used to succeed will now fail.
- The restricted AGENTS.md rendering is not read by any coder config yet (plan step 4 creates it): only the prompt notice reaches the coder.
- Live `Stop-ScheduledTask` child/grandchild check, the AO token elevation read, plan step 4, #1682: unchanged, still open.
- 5.1: the stage and its library parse and `verify-coder-provisioning.ps1` passes under Windows PowerShell 5.1; `verify-coder-narrowing.ps1` and the differential need PowerShell 7 (they use `-Parallel`, `-AsHashtable`).
