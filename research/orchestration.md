1) OPENCODE HEADLESS/SERVER (opencode.ai/docs/server, /docs/sdk, /docs/cli)
- `opencode serve [--port 4096] [--hostname 127.0.0.1] [--cors <origin>] [--mdns]` — defaults 127.0.0.1:4096. HTTP Basic auth via env `OPENCODE_SERVER_PASSWORD` (user defaults to "opencode", override with `OPENCODE_SERVER_USERNAME`). OpenAPI 3.1 spec + Swagger at `http://localhost:4096/doc`.
- REST API: `POST /session` (optional parentID/title), `POST /session/:id/message` (accepts `agent` and `model` per call), `POST /session/:id/prompt_async` (returns 204, fire-and-forget), `POST /session/:id/abort`, `GET /session/:id/children`, SSE at `GET /event` and `GET /global/event`, `GET /global/health` -> {healthy, version}. Multiple clients can attach to one server; parallel agents = parallel sessions.
- SDK: npm `@opencode-ai/sdk` (TypeScript). `createOpencode()` spawns server+client; `createOpencodeClient({baseUrl})` attaches to a running one. `client.session.create(...)` / `client.session.prompt({path:{id}, body:{model:{providerID,modelID}, parts:[...]}})`; parallel sessions via plain Promise.all; structured output via `format:{type:"json_schema", schema:{...}}`. Community Python `opencode-agent-sdk` exists on PyPI.
- Scripting without SDK: `opencode run "prompt" --model provider/model --agent <name> -s <sessionID> --format json --attach http://localhost:4096 --dir <path>`. Persistent server + `--attach` removes cold-start. `opencode session list --format json`, `opencode export` for transcripts.
- GitHub runner mode: `opencode github install` writes .github/workflows/opencode.yml + installs GitHub App; trigger with `/opencode` or `/oc` in issue/PR comments; agent runs `opencode github run` inside YOUR Actions runner, creates a branch and submits a PR. NOTE: this requires GitHub Actions (cloud or self-hosted runner) — not usable fully offline.
- Local model config (opencode.ai/docs/providers): opencode.json provider block: {"provider":{"llamacpp":{"npm":"@ai-sdk/openai-compatible","options":{"baseURL":"http://127.0.0.1:8080/v1"},"models":{"qwen3-coder:a3b":{"limit":{"context":128000,"output":65536}}}}}}. Ollama endpoint http://localhost:11434/v1; docs warn: if tool calls fail on Ollama, raise num_ctx to 16-32k. Docs recommend Qwen-Coder/DeepSeek-Coder variants for reliable tool calling locally.
- Community example (rogs.me, Apr 2026): persistent `opencode serve --hostname 0.0.0.0 --port 4096` as systemd service + opencode-scheduler plugin; three overnight cron jobs (test-gap PRs, docs updates, convention enforcement); results land as PRs reviewed in the morning.

2) OPENCLAW AS ORCHESTRATOR (docs.openclaw.ai)
- Cron (docs.openclaw.ai/automation/cron-jobs): `openclaw cron create "0 7 * * *" "prompt" --name X --session isolated --announce --channel <ch> --to <target>`; schedule kinds at/every/cron; sessions main|isolated|current|session:<custom-id>. Command jobs run shell on the gateway host with `sh -lc` (`--command`, `--command-argv`, `--command-env`, `--timeout-seconds`); require operator.admin. Delivery: --announce / --webhook URL / --none. Config: cron{enabled, maxConcurrentRuns:8, retry{maxAttempts:3, backoffMs}, sessionRetention:"24h"}. Manual: `openclaw cron run <id> --wait --wait-timeout 10m`; history via `openclaw cron runs --id <id>`. Webhooks: POST /hooks/agent (isolated agent turn) and /hooks/wake on gateway port 18789, Bearer token auth.
- Sub-agents (docs.openclaw.ai/tools/subagents): `sessions_spawn` is non-blocking (returns runId), child runs in isolated session `agent:<id>:subagent:<uuid>`, announces result back to parent (result text, status, runtime, token usage, transcript path); parent waits with `sessions_yield` (polling explicitly discouraged). Context modes isolated|fork. Config: agents.defaults.subagents{maxConcurrent:8, maxSpawnDepth:2, maxChildrenPerAgent:5, runTimeoutSeconds:900, model:<cheaper-model>, delegationMode:"suggest"|"prefer"}. Depth-2 workers cannot spawn. /subagents list|log|info; /stop cascades to children.
- Dispatching to OpenCode — three concrete routes: (a) bundled coding-agent skill (github.com/openclaw/openclaw/blob/main/skills/coding-agent/SKILL.md): opt-in `skills.entries.coding-agent.enabled: true`; launches workers with background:true — OpenCode via `opencode run < "$PROMPT"` with pty:true (Claude Code uses `claude --permission-mode bypassPermissions --print`, no PTY); worker MUST report completion via `openclaw message send --channel <ch> --target <t> --message <result>`; skill explicitly says never run agents inside the OpenClaw state dir — use an isolated checkout. (b) ACP runtime (docs.openclaw.ai/tools/acp-agents): `openclaw plugins install @openclaw/acpx`, set acp.enabled=true; supports OpenCode, Claude Code, Codex, Gemini CLI, Copilot, Cursor, Qwen Code etc.; spawn via `/acp spawn opencode --thread auto` or `sessions_spawn({runtime:"acp", agentId})`; per-agent runtime.acp.cwd; WARNING: OpenClaw's sandbox does NOT wrap ACP execution. (c) Community: `npx clawhub install opencode-controller` skill; oh-my-opencode plugin adds a multi-agent fleet inside OpenCode itself (token-heavy — poor fit for local models).
- Windows: OpenClaw officially recommends WSL2 (Ubuntu) for the Gateway; native PowerShell installer and a signed WinUI "Windows Hub" app exist; needs Node 22.16+/24. Gateway must run continuously for cron to fire (default port 18789). WSL2 coexists with Hyper-V (both use the Windows hypervisor platform already enabled for BlarAI); user already has a .wslconfig to cap VM memory.

3) FLEET REALISM ON THIS HARDWARE (the honest answer: 1 active coding agent, maybe +1 light task)
- Memory: 32GB shared LPDDR5X; Arc 140V can use roughly half of system RAM (~16GB) as shared GPU memory. Qwen3-30B-A3B/Qwen3-Coder-30B-A3B Q4_K_M GGUF is ~18.6GB weights — does NOT fit the iGPU budget; needs MoE expert offload to CPU (llama.cpp `--n-cpu-moe`) or a smaller quant; still usable because only ~3B params are active. Qwen3-14B INT4 (~8.5GB) fits comfortably — and already runs on this machine via OpenVINO GenAI.
- Measured datapoints: Intel reports 34 t/s for Qwen3-30B-A3B on a Core Ultra 9 285H Arc iGPU (intel.com Qwen3 article); on Lunar Lake Arc 140V specifically, qwen3:8b Q4_K_M = 17-18 t/s generation, ~99 t/s prefill via IPEX-LLM Ollama (enricomgian gist); CPU-only ~9 t/s. Expect ~10-25 t/s generation and low-hundreds t/s prefill for 14B/30B-A3B class. Agentic coding turns are prefill-dominated; third-party 2026 benchmark measured ~126k tokens per completed aider task (and ~300k for goose) — i.e., one agent task = many minutes on this iGPU; an overnight queue realistically completes ~5-15 tasks, not dozens.
- llama-server sharing: continuous batching is built in; `--parallel N` creates N KV slots and SPLITS total `-c` context across them; slot selection by longest-common-prefix. The key 2026 pattern (fillumina.wordpress.com, May 2026): define multiple model entries in opencode.json pointing at the same server with pinned `id_slot` — main agent on slot 0, all subagents on slot 1 — so subagent prompts don't evict the main session's cache ("two full re-prefills for what should have been zero" on 50k+ sessions otherwise). KV cache quantization `--cache-type-k q8_0 --cache-type-v q8_0` halves KV footprint. On Xe2, llama.cpp SYCL generation is ~2.2x faster than Vulkan (lemongravy.me).
- OpenVINO path (user's home turf): OpenVINO Model Server 2026.x serves OpenAI-compatible chat/completions with continuous batching + paged attention on CPU AND GPU (docs.openvino.ai 2026 continuous_batching demo + agentic demo); the NPU serving path accepts concurrent requests but processes them SEQUENTIALLY (no request batching) — NPU is fine for a single background lane (e.g., embeddings or a 1.5-3B summarizer), not for fleet concurrency.
- Net: two concurrent 14B agents each run at roughly half speed and split context; >2 is counterproductive. A realistic "fleet" here = 1 OpenClaw orchestrator turn (cheap, short prompts) + 1 OpenCode worker doing real coding, processed as a serial queue (OpenClaw cron maxConcurrentRuns/subagents maxConcurrent set to 1-2).

4) ALTERNATIVES (minimal, novice-realistic)
- aider `--watch-files`: watches repo for "AI!"/"AI?" comments and acts on them; most token-efficient agent in 2026 comparisons (~126k tokens, ~257s per task, best accuracy/efficiency balance); auto-commits each change to git (built-in audit trail). Caveat: pair-programming style, not autonomous fleet; Python-based (check Python 3.14 compat at install; may need a 3.12 venv via uv).
- goose (Block, Linux Foundation): Recipes for recurring workflows, no Docker required, MCP support — but measured as very token-hungry (~300k tokens/task) — poor fit for a 15-25 t/s local server.
- Cline: VS Code extension with human approval gates — good interactive safety, not headless orchestration.
- AutoGen/LangGraph: code-level frameworks; overkill for a solo novice vs OpenClaw-cron + opencode-serve.
- Simplest possible alternative to OpenClaw entirely: Windows Task Scheduler or a PowerShell loop calling `opencode run --attach http://localhost:4096 --dir <worktree> "task" --format json` — zero new infrastructure.

5) GIT SAFETY PATTERNS (Windows)
- Canonical rule from 2026 practice: one task -> one branch -> one worktree -> one agent. Worktrees solve FILE collisions, not semantic conflicts — two agents touching the same function merge cleanly into a broken build, so keep task boundaries disjoint and gate merges on tests.
- Novice setup with plain git (works in PowerShell): `git worktree add ..\myapp-fix-logging -b agent/fix-logging` -> point the agent's --dir/cwd at that worktree -> agent commits there -> human gate: `git diff main...agent/fix-logging` + run tests -> merge -> `git worktree remove ..\myapp-fix-logging; git branch -d agent/fix-logging`.
- Windows-specific (laurentkempe.com, Mar 2026): bare-clone layout (project\.git bare + sibling worktree dirs named myapp-feature-auth etc.); Worktrunk tool (`git-wt switch --create my-feature`, `git-wt list`, `git-wt remove`) — alias is git-wt because `wt` collides with Windows Terminal; post-create hooks run restore/build per worktree; psmux for detachable agent terminal sessions. Keep worktree paths short to dodge MAX_PATH; each worktree needs its own node_modules/build dir (avoids file-lock collisions).
- Review gates: tests + a separate checker pass before merge ("gate verdict from a checker agent only"); review every agent line like a colleague's PR. OpenClaw's coding-agent skill guidance: agents always work in an isolated checkout, never the orchestrator's own state dir.

## RECOMMENDATION
For THIS machine (32GB Lunar Lake, Arc 140V, Windows 11, no Docker), build the minimal pipeline and accept that the "fleet" is a serial queue with 1 active coding agent:

1. Model server (pick ONE, you only have memory for one): Option A — your home turf: OVMS 2026.x serving Qwen3-14B INT4 (already proven on your Arc 140V) on http://localhost:8000/v3 OpenAI-compatible with continuous batching on GPU. Option B — zero-download start tonight: llama.cpp SYCL build, `llama-server -m C:\Users\mrbla\.ollama\models\blobs\sha256-998e730e... -c 65536 --parallel 2 --cache-type-k q8_0 --cache-type-v q8_0 --jinja --port 8080` reusing your existing qwen2.5-coder:14b-q6_K GGUF blob (verified loadable). If you want Qwen3-Coder-30B-A3B, use Q4 with `--n-cpu-moe` expert offload — it won't fit the ~16GB iGPU share otherwise. Skip the NPU for agents (sequential serving only).
2. Worker: `npm i -g opencode-ai`, opencode.json with `@ai-sdk/openai-compatible` provider -> your local baseURL; run `opencode serve` (127.0.0.1:4096, set OPENCODE_SERVER_PASSWORD) as a persistent process; dispatch with `opencode run --attach http://localhost:4096 --dir <worktree> --format json "task"`. If you use llama-server with --parallel 2, pin OpenCode subagents to slot 1 via a second model entry with id_slot (fillumina pattern) so they don't evict the main session's KV cache.
3. Orchestrator: OpenClaw Gateway in WSL2 Ubuntu (officially recommended path; coexists with your Hyper-V/BlarAI — cap WSL memory at ~6GB in .wslconfig so the model keeps RAM). Enable the bundled coding-agent skill (`skills.entries.coding-agent.enabled: true`) and create nightly isolated cron jobs (`openclaw cron create "0 2 * * *" "<task>" --session isolated --announce`). Set subagents maxConcurrent: 1 and cron maxConcurrentRuns: 1 — that is the honest limit of this box. Caveat: OpenCode would then live inside WSL2 too (cleanest), with your repos under \\wsl$ or a Linux-side clone; if you want everything Windows-native, replace OpenClaw with a Task Scheduler + PowerShell queue script calling opencode run — genuinely adequate for a solo novice and one less moving part.
4. Safety: one task -> one branch -> one worktree -> one agent. `git worktree add ..\repo-taskname -b agent/taskname`, agent works only there, merge gate = tests pass + you read the diff next morning, then `git worktree remove`. Never let the agent run in your main checkout or in OpenClaw's state dir.
5. Skip for now: oh-my-opencode and goose (token-hungry, built for cloud-priced tokens), opencode github runner (needs GitHub Actions, not offline), AutoGen/LangGraph (framework overhead). aider --watch-files is worth keeping as a complementary interactive tool given it is the most token-efficient harness measured in 2026 — good fit for a 15-25 t/s local server.

Throughput expectation to plan around: ~10-25 t/s generation, prefill-dominated agent turns of ~100k+ tokens -> ~5-15 completed tasks per night, reviewed by you each morning. That is what a realistic local fleet looks like on this hardware.

## CAVEATS
- Honest concurrency ceiling: 2 KV slots on one 14B model is the practical max; both halve speed and split context. Any blog promising 4-8 parallel local agents assumes a 64GB+ machine or discrete GPU. The Intel 34 t/s Qwen3-30B-A3B figure was on a Core Ultra 9 285H (Arrow Lake-H), not your 258V — expect somewhat less on Lunar Lake.
- 30B-A3B Q4_K_M (~18.6GB) does not fit the Arc 140V's ~16GB shared-memory budget; CPU expert offload works but cuts speed and eats the RAM that OpenClaw/WSL2/OS also need. With WSL2 (+your existing Hyper-V BlarAI VM) running, total memory pressure on 32GB is real — cap WSL and watch for the model server getting paged.
- OpenClaw moves fast; config keys (skills.entries.coding-agent.enabled, agents.defaults.subagents, @openclaw/acpx) were verified against docs.openclaw.ai as of June 2026 but may rename — re-check at install time. Native Windows (non-WSL) OpenClaw exists but docs steer to WSL2; cron requires the gateway running 24/7.
- The coding-agent skill's worker launch uses `bypassPermissions`-style full-autonomy modes — only safe inside dedicated worktrees with the review gate; OpenClaw's sandbox explicitly does NOT wrap ACP-spawned harnesses.
- Your qwen2.5-coder blobs are 2024-era models; tool-calling reliability in OpenCode will be noticeably worse than Qwen3-Coder/Qwen3-14B — fine for a smoke test, plan one ~9-18GB download (Qwen3-Coder-30B-A3B or Qwen3-14B GGUF/OpenVINO INT4) while online.
- aider on Python 3.14 may need a pinned 3.12 venv (uv makes this trivial); its efficiency numbers come from one third-party benchmark with unclear methodology.
- opencode github runner mode requires GitHub Actions infrastructure — incompatible with fully-offline operation unless you run a self-hosted runner, which is more complexity than it is worth here.
- Several sources are personal blogs (fillumina, rogs.me, laurentkempe, lemongravy) — patterns verified as plausible and mutually consistent, but exact flags/perf numbers were not reproduced on your hardware.
